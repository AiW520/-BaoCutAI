## 1. 定位与原则

### 1.1 用户得到什么

视频的权威状态在 `video.db`（SQLite，[架构设计 §5.1](../../architecture/architecture-design.md#51-存储分层)）。它对 BaoCut 合适，对 git 不合适：二进制文件看不出改了什么、合并不了，打开中的视频还有一部分最新提交只在 `-wal` 里，直接提交会得到不一致的副本。

本方案不改存储，而是让 BaoCut 在每个视频目录里额外写一份**工作区快照**：当前状态的确定性文本。每个项目是一个 git 仓库，BaoCut 在工作告一段落时自动提交。用户因此得到：

| 收益 | 怎么得到 |
| --- | --- |
| **看得见改了什么** | 快照按行稳定排版，`git diff` 一行对应一个片段、一句字幕或一个文稿段落 |
| **回到任何一个版本** | 版本记录里选一个提交「恢复到这个版本」，作为一笔可撤销的编辑应用，不改写历史（§5.4） |
| **换机器、备份、协作** | 用户自己 `git push` 到任何远端；在另一台机器克隆后，BaoCut 从快照重建视频（§5.2） |
| **智能体的改动有据可查** | 每个提交写明这一段里哪些会话、哪些编辑改了哪些视频（§4.4） |

### 1.2 两层历史

「每次操作都留痕」与「提交不要零碎」分别由两层承担：

| 层 | 粒度 | 在哪 | 用途 |
| --- | --- | --- | --- |
| **撤销历史** | 每一笔编辑事务 | `video.db` 的 `transactions` 与 `undo_records`（[命令与协议规范 §3](../../spec/command-protocol-spec.md#3-事务与严格的版本校验)） | 撤销、重做、看这部视频的每一步 |
| **版本记录** | 一个工作段：一次或多次智能体回合与手工编辑合在一起 | 项目的 git 仓库 | 里程碑、对比、恢复、同步与备份 |

每一笔操作都会进入版本记录：它总在下一个提交里，提交说明逐项列出它（§4.4）。但提交按工作段合并发生（§4.1），一小时的编辑通常是几个提交，不是几十个。

### 1.3 原则〔G〕

- **`video.db` 仍是唯一的写入端。** 快照由 VideoEngine 从已提交的状态生成，是派生物（视频格式规范 §3.1「不是第二个写入端」的同一条规则）。外部对快照的改动只能经 VideoEngine 的一笔事务进入视频（§5.3），不直接改库。
- **不改写历史，不碰网络。** BaoCut 只做 `init`、`add`、`commit` 与只读查询；不 `push`、`fetch`、`pull`、`merge`、`rebase`、`reset`、`checkout`、`--amend`，不删分支与标签。恢复版本是向前的新提交。
- **不碰用户的东西。** 用户已暂存或尚未提交的改动、用户的忽略规则、用户的分支，BaoCut 都不动（§4.3、§4.5）。
- **不阻塞编辑。** 没有 git、提交失败、仓库处在合并中，项目与视频照常工作；版本记录只报告状态（§4.6）。
- **大文件不进 git。** 超过门槛的文件不自动提交（§2.4）。
- **提交时不执行仓库里带来的命令。** 钩子、fsmonitor、签名程序一律不跑（§6）。

### 1.4 不做什么

- 不把 `video.db` 换成 JSON 与 JSONL。多实体原子提交、幂等与回执、撤销记录与 outbox 同一事务落盘（[架构设计 §5.2](../../architecture/architecture-design.md#52-写入发布与崩溃一致性)）都靠数据库；把逐笔的事务日志放进 git 只会让仓库变大、diff 全是噪声。
- 不做视频级的三方合并。两边都改了同一部视频时按整部视频选一边（§5.1），不逐行合并时间线。需要合并时间线是另一个功能。
- 不托管远端、不管凭据。推送、拉取由用户在 git 里自己做。
- 不属于任何项目的会话（会话自己的文件夹）不建仓库、不写快照。

## 2. 项目与仓库

### 2.1 三种情形

打开或新建项目时，BaoCut 用 `git rev-parse --show-toplevel` 判断项目目录在不在一个仓库里，分三种情形：

| 情形 | 是否 `git init` | 提交范围（§4.3） | 忽略与属性规则写在 |
| --- | --- | --- | --- |
| **新建项目**：BaoCut 新建的空文件夹 | 是 | **全量**：项目里的所有改动，受 §2.4 门槛约束 | 提交进仓库的 `.gitignore` 与 `.gitattributes` |
| **已有文件夹，不在仓库里** | 是（主目录等位置除外，§2.2） | **归属**：只提交 BaoCut 写的或这段工作改的路径；文件夹里原有的文件是用户的，不自动收进来 | `.git/info/exclude` 与 `.git/info/attributes` |
| **已有文件夹，已在仓库里**（项目目录是仓库根，或是更大仓库的子目录） | 否，沿用 | **归属**，且只在项目目录内 | `.git/info/exclude` 与 `.git/info/attributes` |

- 模式记在 Runtime Store 的项目登记里（[架构设计 §5.1](../../architecture/architecture-design.md#51-存储分层)），不写进 `.bcut/project.json`。克隆下来的仓库在新机器上第一次打开时按第三种情形处理，归属模式，保守。
- 项目里嵌套的其他仓库（含子模块）不进版本：全量模式把它们的目录写进 `.git/info/exclude` 的 BaoCut 块，归属模式本来就不会提交它们。
- 机器本地的 `.git/info/*` 里，BaoCut 只改自己的块（`# >>> BaoCut` 到 `# <<< BaoCut`），每次打开项目时补齐；块外的内容不动。

### 2.2 初始化

- **新建项目**：在 `projects.create` 建好目录、写好标记并登记之后执行 `git init`。分支名沿用用户的 `init.defaultBranch`。接着写入 `.gitignore`、`.gitattributes`（§2.3），并提交第一个提交「创建项目」。`git init` 不能早于项目创建成功，否则创建失败时的回滚（只删空目录）会留下一个半成品文件夹。
- **已有文件夹不在仓库里**：打开时 `git init`，只写 `.git/info/*` 的 BaoCut 块，不在用户的文件夹里新建 `.gitignore`。第一个提交等到第一个提交点（§4.1），只含 BaoCut 的路径。
- **不在这些位置 init**：用户主目录、系统的标准用户文件夹（桌面、文稿、下载、影片、音乐、图片，以及 Windows 上对应的已知文件夹），以及卷或盘符的根。在这里建 `.git` 会让下面所有文件夹在 IDE、shell 与其他工具看来都处在一个仓库里。这时按没有仓库处理，状态说明原因；用户确实需要时可以自己 `git init`，BaoCut 下次打开时按「已在仓库里」处理。
- **已在仓库里**：不 init，只补 `.git/info/*` 的 BaoCut 块。
- 项目目录不可写、git 不可用时不初始化，项目照常打开，版本记录显示原因（§4.6）。之后条件满足时，在下一次打开项目时补做。
- 用户关掉了这个项目的版本记录（§4.2）时不初始化；已有的 `.git` 不删。

### 2.3 忽略规则与属性

新建项目提交进仓库的 `.gitignore`（文件里的注释用英文，与代码字符串的规则一致）：

```gitignore
# BaoCut: machine-local state and rebuildable output
.bcut/
.bcut-trash/
**/video.db
**/video.db-*
**/video.lock
**/movie.db
**/movie.lock
**/blobs/.staging/
.baocut-out/
**/.baocut-out/
**/.baocut-export-*/
.baocut-import-*/
**/.*.partial
**/exports/
.DS_Store
Thumbs.db
```

- `.bcut/` 不进版本：项目标识是机器本地的，副本检测会给副本改写新的 `projectId`（[架构设计 §5.1](../../architecture/architecture-design.md#51-存储分层)），提交它会在克隆之间来回改、来回冲突。
- `video.db` 及其 `-wal`、`-shm`、`-journal` 和 `video.lock` 不进版本。`video.lock` 每次打开都改写内容。
- 导出的成片（`exports/`）是可以重新导出的产物，默认不进版本。
- `blobs/` 本身不忽略：收进来的素材按内容寻址、写一次不再变，小于门槛的提交一次即可，大的由 §2.4 挡住。

`.gitattributes`：

```gitattributes
**/.bcut-snapshot/** text eol=lf merge=binary linguist-generated=true
```

- `eol=lf`：Windows 上 `core.autocrlf` 不能把快照改成 CRLF，否则检出后摘要对不上，被误判为外部改动（§5.1）。
- `merge=binary`：两边都改了同一部视频的快照时，git 报冲突而不逐行拼接。逐行拼出来的时间线可能是合法 JSON，却是错的剪辑。
- `linguist-generated`：代码托管网站的 diff 默认折叠快照。

归属模式把同样的规则写进 `.git/info/exclude` 与 `.git/info/attributes` 的 BaoCut 块。用户自己的 `.gitignore` 优先：被用户忽略的路径 BaoCut 不加 `-f` 强行提交。

### 2.4 大小门槛

- 单个文件超过 `projects.history.maxFileMiB`（默认 50 MiB）不自动提交。全量模式把它写进 `.git/info/exclude` 的 BaoCut 块，让 `git status` 保持干净；归属模式直接跳过。两种模式都在提交说明里列出跳过的文件与大小（§4.4）。
- 仓库已经用 Git LFS 跟踪的路径（`git check-attr filter` 为 `lfs`）不受门槛限制，照常 `add`，由 LFS 处理。BaoCut 不替用户设置 LFS。
- 已经被跟踪的文件后来超过门槛：不再自动提交它的改动，提交说明里注明。
- 被跳过的收进来的素材在克隆后缺失，视频照常打开、素材标为缺失（§5.2）。

### 2.5 没有 git 的时候

- 快照照写（§3.4）。用户用别的版本管理或同步盘时同样有用。
- 不初始化、不提交。项目设置与版本记录显示「没有找到 git」，并链接到工具页说明怎么安装（[架构设计 §12.9](../../architecture/architecture-design.md#129-受管外部工具与安装动作)）。
- 检测到 git 之后（用户安装了它，或在工具页指定了路径），下一次打开项目时补做 §2.2。

## 3. 工作区快照

### 3.1 位置与布局

```text
<video-dir>/
  video.db, video.lock, blobs/      # 不变
  .bcut-snapshot/
    video.json                      # 视频的当前状态：VideoSnapshot 的投影（§3.2）
    documents/<documentId>.json     # 每个文档当前版本的正文，一个文档一个文件
```

- 放在点目录里：Space 的扫描、`projects.files.list` 与文件监视都跳过点开头的名字（`isIgnoredName`），快照不会作为用户内容出现。代价是现有的递归监视看不到它的变化，外部改动另行检测（§5.1）。
- 文档文件名不带版本号。git 按路径追踪同一个文件，改一句话就是同一个文件里改一行。这一点与便携包的 `documents/<id>/<revision>.json` 不同（[视频格式规范 §8](../../spec/video-format-spec.md#8-便携包)）。
- 每个文件先写临时文件再改名替换，单个文件原子；一组文件的一致性由 `video.db` 元数据里的摘要保证（§5.1）。

### 3.2 内容：当前状态的投影

`video.json` 由 VideoEngine 的 `VideoState::snapshot`（[视频格式规范 §3.1](../../spec/video-format-spec.md#31-videosnapshot)）投影而来，只在下面几处不同：

- 文件头：`format: 'baocut.workspace-snapshot'`、`schemaVersion: 1`、`videoSchemaVersion`、`videoId`、`name`。不写 `projectId`（机器本地的标识，§2.3）。
- **去掉每次提交都变的计数**：顶层 `revision`、序列的 `revision`、`eventSeq`、`ownerGeneration`。否则每个提交都在头部改一行，两边各改一点也必然冲突。写入时的修订号记在 `video.db` 的元数据里（§5.1）。
- **只留当前**：文档头只保留当前版本，素材版本只保留当前实体引用到的那些。检查点不写入：命名的历史状态在版本记录里就是提交（§7）。
- 文档正文只写当前版本，`documents/<documentId>.json` 的内容就是这个版本的正文。
- 不写每次保存都会变的时间（如 `updatedAt`）。只在创建时写一次、之后不变的时间（`createdAt`、`importedAt`、链接时的 `modifiedAt`）保留，它们不会在提交之间变化。

快照里没有撤销历史、回执与 outbox。从快照重建的视频的撤销历史从重建开始（§5.2）。

### 3.3 行稳定的序列化

快照文本由 VideoEngine 用 Rust 生成，Runtime 只搬运、不重新序列化。Node 的 `JSON.parse` 再 `JSON.stringify` 会把整数样子的键提到前面，改变顺序。规则：

- UTF-8，换行 LF，文件以换行结尾。
- 对象的键按字典序。引擎的映射是 `BTreeMap`，`serde_json` 不开 `preserve_order`。数组保持模型规定的顺序：轨道按顺序再按 ID，片段按轨道、开始位置、ID，标记按帧再按 ID。
- **前两层展开，第三层起每个值写成一行**。第一层是根对象，第二层是它的成员，每个键一行，缩进两个空格；第三层及更深的值压成一行紧凑 JSON。于是 `video.json` 里一个片段、一个标记、一个素材版本各占一行；转录文档里一个句段连同它的词时间占一行。
- 同一状态必须得到逐字节相同的文本。这是序列化器的单元测试。

改一个片段的入点，diff 是一行；给一句字幕改一个字，diff 也是一行。

### 3.4 何时写

- 每个提交点提交之前（§4.1），为这一段里有过改动的视频写。
- 关闭视频时（最后一个打开者离开、空闲关闭），在放下写锁之前写，与 blob GC 同一时机（[架构设计 §5.2](../../architecture/architecture-design.md#52-写入发布与崩溃一致性)）。这样没有人打开视频时，磁盘上的快照总等于库里的状态。
- 不逐笔写。转录正文可以有 1 MB，逐笔写是白白的 I/O。
- 只重写内容变了的文件：按每个文件的摘要比较，相同的不碰，保留修改时间。
- 关掉了版本记录、或者没有 git 的项目照样在关闭视频时写快照（§2.5）。不属于项目的视频不写。

### 3.5 链接素材的路径

- 项目内的链接素材本来就按相对视频目录的路径记录（[视频格式规范 §4.2](../../spec/video-format-spec.md#42-存储位置)），克隆后照常有效。
- 项目外的链接素材：在用户主目录下的写成 `~/` 开头的路径，其余（外接盘、网络共享）保留绝对路径。同时保留文件名、内容摘要与大小，供另一台机器上 `relinkAsset` 找回。
- 这意味着推送出去的快照里有项目外素材的路径。版本记录的设置里说明这一点。完全不想带路径的用户用便携包分享（它把路径换成占位，[视频格式规范 §8.2](../../spec/video-format-spec.md#82-规则)）。

## 4. 提交

### 4.1 提交点

有待提交的改动时，下面任何一个条件成立就提交一次。默认的「按工作段」频率（§4.2）下：

| 提交点 | 说明 |
| --- | --- |
| **项目安静满 5 分钟** | 没有进行中的智能体回合，没有写进这个项目的任务在跑，5 分钟内没有新的编辑事务 |
| **连续工作满 30 分钟** | 一直有活动时，在下一个回合结束或下一笔事务之后提交一次，一个提交不无限变长 |
| **关闭项目、退出 BaoCut** | 立即提交，不等安静期 |
| **保存版本** | 用户或智能体显式保存一个具名版本，立即提交，提交说明用这个名字 |
| **恢复版本之前、之后** | 先把手上的改动提交，再恢复，恢复本身再提交一次（§5.4） |

- **回合进行中不提交。** 智能体可能正在写文件、可能自己在跑 git。硬边界撞上进行中的回合时推迟到回合结束；退出 BaoCut 会中止回合，中止后提交。
- 关闭单个视频不是提交点，只写快照（§3.4）。用户在两三部视频之间来回切换不会切出一串提交。
- 没有改动不提交，不产生空提交。
- 会话收进项目时，旧文件夹先变成指向项目的链接，剩下的文件由后台搬入（[架构设计 §3.10](../../architecture/architecture-design.md#310-会话与项目的绑定)）。搬入完成前到了提交点就先提交已有的，搬进来的文件由下一个提交点带上。
- 安静期与最长时长是可调的产品参数（[文档约定](../../README.md#规范用语)），不是保证。

### 4.2 提交频率

项目设置里的「自动提交」，全局默认值是设置 `projects.history.cadence`，可按项目覆盖：

| 取值 | 行为 |
| --- | --- |
| `segment`（默认） | §4.1 的全部提交点 |
| `turn` | 每个改了项目的智能体回合结束时提交一次；手工编辑仍按安静期合并 |
| `manual` | 只在保存版本与恢复版本时提交；快照照写 |

`projects.history.enabled`（默认开）关掉整个版本记录：不初始化、不提交，快照照写。

### 4.3 提交哪些文件

**全量模式**（BaoCut 新建的项目）：

1. 为这一段改过的视频写快照（§3.4）。
2. `git status --porcelain=v2 -z --untracked-files=all` 列出改动；超过门槛的写进 exclude 块（§2.4），嵌套仓库同样处理。
3. `git add -A -- <项目目录>`，然后 `git commit`。用户在 BaoCut 外放进项目文件夹的文件也随之进入版本。这是新建项目的含义：整个文件夹由 BaoCut 版本化。

**归属模式**（已有文件夹）：只提交下面三类路径的并集，并且只在项目目录内：

1. 这一段改过的视频的 `.bcut-snapshot/`（含删除：视频移进回收站后，它的快照文件从版本里删除），以及这些视频 `blobs/` 下小于门槛、且没被用户规则忽略的条目。
2. BaoCut 自己的写入口这一段写过的文件：新建文件（`projects.files.create`）、存进项目的链接下载与导入、存进项目的生成结果、文档、幻灯片与设计稿的保存。各写入口把路径登记给 ProjectHistory（§8.2）。
3. 智能体回合改动的路径：回合开始时记下仓库里的脏路径集合与各自的内容摘要（`git hash-object`），回合结束时再取一次。回合前干净、回合后变了的路径算这个回合的。**回合前就有未提交改动的路径不提交**：分不清哪部分是用户自己的，在提交说明里注明「含回合前的改动，未自动提交」。

提交命令用 `--only`：

```text
git add -- <paths>
git commit --only -F <message-file> -- <paths>
```

`--only` 只提交给出的路径，用户已经暂存的其他改动原样留在暂存区。

用户在 IDE 里同时改的代码不在三类之内，不会被归属模式提交。

### 4.4 提交说明

提交说明是给人看的文字，用提交时的界面语言，模板在多语言目录里（[仓库约定 §5](../../repo-conventions.md#5-文案与多语言)）。由模板拼出，不调用模型。

- **标题**按这一段的主要内容：只有一个智能体回合时用会话或任务的标题；只有手工编辑时用「<视频名>：<第一项编辑>等 N 项」；混合时按视频列出名字并注明回合数与编辑数。保存版本用用户给的名字。
- **正文**按视频分组，每组列出修订号范围、这一段的编辑标签（同名合并计数，超过 20 行折叠为「另有 N 项」）。编辑标签有 `labelRef` 的按界面语言显示，智能体传入的自由文本原样保留。正文还列出智能体回合（会话标题）、跑完的任务（种类与结果）、新增与删除的文件数，以及被跳过的文件：超过门槛的、含回合前改动的。
- **尾注**（键固定为英文，供程序识别）：

```text
BaoCut-Commit: segment | turn | save | restore | init
BaoCut-Video: <videoId> r<from>..r<to>        # 每部改过的视频一行
BaoCut-Conversation: <conversationId>         # 每个回合一行
```

- **作者**：仓库或全局配置了 `user.name` 与 `user.email` 时用用户自己的身份，提交就是用户的；没配置时用 `BaoCut <baocut@localhost>`，不从系统用户名或主机名拼一个邮箱。

### 4.5 与用户、智能体共用仓库

- **锁**：`.git/index.lock` 存在说明有人在用 git（用户、IDE 或智能体）。BaoCut 等 2 秒重试，最多 5 次，仍不行就推迟到下一个提交点，状态里显示「仓库正被占用」。**任何时候都不删别人的锁文件。**
- **特殊状态**：仓库在合并、变基、拣选、还原或二分中（`MERGE_HEAD`、`rebase-merge/`、`rebase-apply/`、`CHERRY_PICK_HEAD`、`REVERT_HEAD`、`BISECT_LOG`），或 HEAD 处于分离状态时，自动提交暂停，快照照写，状态说明原因。用户完成操作后自动恢复。
- **分支**：提交到当前分支。用户切换分支后快照随之变化，按外部改动处理（§5.3）。
- **智能体自己的 git**：智能体可以照常 `git status`、`git commit`。BaoCut 不在回合中提交（§4.1），两者不抢锁。智能体自己提交了快照文件也没关系，下一个提交点没有改动就不提交。

### 4.6 失败与暂停

| 情况 | 行为 |
| --- | --- |
| 没有 git | 不初始化、不提交；快照照写；状态「没有找到 git」（§2.5） |
| 锁被占用、仓库特殊状态 | 推迟或暂停（§4.5） |
| 仓库本地配置会执行命令 | 暂停，等用户在项目设置里显式启用（§6） |
| 提交失败（磁盘满、权限、git 报错） | 记日志，状态显示最近的错误；待提交的改动并入下一个提交点；不重试成死循环 |
| 快照写入失败 | 这部视频本次不提交，状态说明；`video.db` 不受影响 |

版本记录的失败从不让编辑、智能体回合或任务失败。数据在 `video.db` 里，版本记录只是没跟上。

## 5. 从快照回到视频

### 5.1 判定

`video.db` 的元数据（不属于修订内容，写它不产生新版本）记两样：`snapshotRevision`，即最后一次写快照时的修订号；`snapshotDigest`，即那一组快照文件的摘要。摘要按规范化后的文本计算（换行统一成 LF），文件名排序后逐个摘要再整体摘要。

打开视频时，以及打开中的视频的快照目录有变化时（每部打开的视频单独监视自己的 `.bcut-snapshot/`，不依赖跳过点目录的递归监视），按下表处理：

| 库领先（当前修订 > `snapshotRevision`） | 快照被改（磁盘摘要 ≠ `snapshotDigest`） | 处理 |
| --- | --- | --- |
| 否 | 否 | 一致，什么也不做 |
| 是 | 否 | 正常：BaoCut 还没写快照，下一个提交点写 |
| 否 | 是 | **外部改动**：导入为一笔可撤销的事务（§5.3） |
| 是 | 是 | **冲突**：不自动合并（§5.3） |
| 没有 `video.db` | 有快照 | **重建**（§5.2） |

- BaoCut 自己写快照也会触发监视；摘要与元数据相同，什么也不做。
- 快照解析不了（被手改坏了、有冲突标记）或 `schemaVersion` 高于已知时不导入、不覆盖：视频按库里的状态照常打开，状态说明快照不可用。这时 BaoCut 下一次写快照前先让用户选择保留哪边，不静默覆盖用户的文件。
- git 处于合并冲突中（`merge=binary` 让快照停在冲突状态）时，自动提交本来就暂停（§4.5），同一部视频按冲突处理。

### 5.2 只有快照：重建

在另一台机器克隆、或者 `video.db` 被删掉时，视频目录里只有 `.bcut-snapshot/`：

- Space 扫描把「有 `.bcut-snapshot/video.json`、没有 `video.db`」的目录列为视频，状态是「待重建」。
- 打开项目时，后台与认领视频同一个预处理流程（[架构设计 §5.1](../../architecture/architecture-design.md#51-存储分层)「打开项目时预处理它的视频」）逐个重建，用户打开视频时也会触发。
- 重建是 VideoEngine 的新操作 `videos.rebuildFromSnapshot`，就地创建 `video.db`，**保留快照里的 `videoId`**。之后照常按所属项目认领：同一项目里已有同一个 `videoId` 的目录时，按副本处理、分配新标识。这与便携包导入不同，导入要求目标目录不存在、总给新标识。
- 文档按当前版本导入。收进来的素材在 `blobs/` 里有就引用；没有（超过门槛没进 git）就标为缺失。链接素材照常解析，找不到也标为缺失，由用户或智能体 `relinkAsset`。
- 修订号从 1 开始，撤销历史从重建开始，不能撤销到重建之前。更早的历史在 git 里。

### 5.3 快照被外部改了：导入

用户 `git pull`、切换分支、`git checkout -- <path>`，或者手改了快照文件：

- **只有快照被改**：VideoEngine 的 `videos.applySnapshot` 比较当前状态与磁盘上的快照，按实体与文档算出差异，作为**一笔**事务提交。标签是「外部变更」，`actor` 是 `system:history`，可撤销。撤销后库领先，下一个提交点会把快照写回撤销后的状态，相当于用户拒绝了这次外部改动。
- **两边都改了**：不导入、不覆盖。视频以库里的状态照常可编辑，版本记录里提示这部视频有冲突，给两个选择：
  - **保留 BaoCut 里的**：下一个提交点用库的状态覆盖快照。
  - **用磁盘上的**：按上一条导入。BaoCut 里的改动仍在撤销历史里，可以撤销回来。
- 用户没有选择之前，这部视频的快照不被重写，也不进提交。
- 导入后素材缺失的处理同 §5.2。

### 5.4 恢复到某个版本

版本记录里选一个提交，对某部视频「恢复到这个版本」：

1. 先在当前位置做一次提交点（§4.1），手上的改动不丢。
2. 用 `git show <commit>:<path>` 把那个提交的快照读进临时目录。工作区不检出，HEAD 不动。
3. `videos.applySnapshot` 按 §5.3 作为一笔可撤销事务应用，标签「恢复到 <提交标题>」。那个版本引用、现在已被 GC 的收进来的素材，如果那个提交里有它的 blob，就从 git 取回、经 staging 发布；没有就标为缺失。
4. 立即提交，`BaoCut-Commit: restore`。

整个项目回到某个提交（多部视频与项目文件一起）是 git 自己的事，用户可以在 git 里做。BaoCut 随后按 §5.3 导入每部视频的变化。

## 6. 安全

用户可以把任何已有文件夹打开为项目，包括从别处下载的仓库，而 git 会执行仓库本地配置里的命令。产品设计规定打开项目不弹信任确认（[产品设计 §3.2.1](../../product/product-design.md#321-起始状态ux-01)），所以自动提交本身要做到不执行仓库带来的命令：

- 每次调用都带 `-c core.hooksPath=<BaoCut 的空目录>`，提交加 `--no-verify`，钩子（包括 `prepare-commit-msg`、`post-commit`）一律不跑。用户靠钩子做的检查不覆盖自动提交，这是有意的。
- `-c core.fsmonitor=false`、`-c commit.gpgSign=false`、`-c tag.gpgSign=false`、`-c maintenance.auto=false`、`-c gc.auto=0`；环境变量 `GIT_TERMINAL_PROMPT=0`；只读查询加 `GIT_OPTIONAL_LOCKS=0`；提交说明用 `-F` 从文件读，不启动编辑器、不用分页器。
- 参数是数组、不经 shell，在自己的进程组里运行，超时整组终止（与受管外部工具的执行规则相同，[架构设计 §12.9](../../architecture/architecture-design.md#129-受管外部工具与安装动作)）。
- **过滤器**：`.gitattributes` 引用、在仓库本地配置（`git config --local`）里定义的 `filter.<name>.clean|smudge|process` 会在 `git add` 时执行。它们不能一律置空，因为 git-crypt 这类工具就靠本地过滤器加密，置空会把明文提交进去。所以本地配置里有过滤器定义、`include.path` 或 `includeIf` 时，自动提交暂停，状态说明原因，用户在项目设置里显式启用后才继续。全局与系统配置里的过滤器（例如用户自己装的 Git LFS）照常生效。本地配置的修改时间变了就重新检查。
- 不读取、不传递凭据，不访问网络。

## 7. 界面、多端与智能体

用户可见的部分（实施前先做原型）：

- **项目设置**：版本记录的开关、提交频率（§4.2）、当前状态（正常 / 暂停及原因 / 没有 git / 最近一次提交的时间与标题），以及项目外素材路径会进入快照的说明（§3.5）。
- **版本记录面板**：按项目或按视频（`git log -- <video-dir>/.bcut-snapshot`）列出提交：标题、时间、改了哪些视频。单个提交可以「恢复到这个版本」（§5.4）。
- **保存版本**：编辑器与会话里都能把当前状态存成具名版本。它同时建一个检查点（[视频格式规范 §3.11](../../spec/video-format-spec.md#311-检查点本规范补全)），并立即提交。
- **冲突与外部变更**：视频有冲突时，编辑器顶部给出 §5.3 的两个选择；外部变更导入后在历史里显示为一笔「外部变更」。

多端（[开发流程 §4.1](../../development-workflow.md#41-跨平台系统集成)）：

| | macOS | Windows | Web |
| --- | --- | --- | --- |
| git 在哪 | Runtime 所在机器的 PATH（登录 shell 的 PATH）；`/usr/bin/git` 只有在 `xcode-select -p` 成功时才用，否则它是会弹出安装开发者工具的占位程序 | PATH 里的 `git.exe`，Git for Windows 的 `cmd\git.exe`；按 PATHEXT 查找，拒绝 `.cmd`、`.bat` | 不在浏览器里；提交发生在 Runtime 所在的机器上 |
| 路径 | POSIX | 盘符、UNC、`\\?\` 扩展路径交给 git 前按既有转换入口处理；仓库内路径一律 `/` 分隔 | 不显示本机路径 |
| 换行 | LF | 快照靠 `eol=lf` 属性固定为 LF（§2.3），摘要按规范化文本计算 | — |
| 界面 | 全部 | 全部 | 状态、版本记录与恢复可用；不提供「在文件夹中显示仓库」这类本机动作 |

智能体：

- 内置 skill 说明 BaoCut 会在工作段结束时自动提交，智能体不需要也不应该手动提交快照，不要在视频打开时 `git checkout` 或 `git reset` 快照文件；用户要「回到某个版本」时用恢复工具，不要改快照。
- 智能体工具（二期）：`project_history` 列出提交、读某个提交的改动摘要；`video_restore_version` 恢复版本；`project_save_version` 保存具名版本。外部智能体经 CLI 与 MCP 用同一组工具（[Agent 能力面设计](../agent-surface/agent-surface-design.md)）。

## 8. 实现

### 8.1 VideoEngine

- **快照投影与序列化**：在 `VideoState::snapshot` 之上加投影（§3.2）与行稳定序列化器（§3.3），放在 `crates/video-engine`。便携包仍用它原来的快照，两者共用投影前的部分。
- **`videos.writeSnapshot { path }`**：只能由持有写锁的一方调用。写 `.bcut-snapshot/`，只替换内容变了的文件，在库的元数据里记 `snapshotRevision` 与 `snapshotDigest`，返回改了哪些文件。
- **`videos.rebuildFromSnapshot { path }`**：目录里没有 `video.db` 时就地建库（§5.2），之后照常认领。
- **`videos.applySnapshot { path, snapshotDir }`**：按实体与文档求差，作为一笔带撤销记录的事务提交（§5.3、§5.4）；`snapshotDir` 可以是临时目录。
- **`videos.snapshotStatus { path }`**：返回 §5.1 判定需要的修订号与摘要，只读，不取锁。

### 8.2 Runtime：ProjectHistory

新模块 `packages/runtime-core/src/project-history/`，每个项目一个串行队列：

- **输入**。现在没有统一的项目写入总线，所以分别接：
  - `VideoService.onChange`。它的语义是「修订变了」，不是「一笔事务」：重新同步时会合并，引擎重启后的重新打开也不触发，所以只用来标记「这部视频有待写快照」，标签从 `history.list` 按修订号范围取。
  - 视频的新建、便携包导入、认领与移进回收站。这些操作不产生事务事件，需要在 VideoService 与回收站流程里显式通知。
  - Harness 的回合开始与回合结束（`turn-finished`），按会话所属的项目归类。
  - `JobManager` 的任务结束。任务没有 `projectId`，由 `videoId`、提交者或输出路径推出所属项目。
  - BaoCut 自己的写入口登记的路径（§4.3 第 2 类）。
- **调度**：§4.1 的计时器与硬边界；关闭项目与退出时同步完成最后一次提交，有超时。
- **归属**：回合级的脏路径基线与比较（§4.3 第 3 类）。
- **提交**：按 §6 的参数调用 git；用 §4.4 的模板组织提交说明；更新状态。
- **监视**：打开中的视频监视各自的 `.bcut-snapshot/`，按 §5.1 判定。
- **初始化**：`projects.create` 与 `projects.open` 在写标记、登记之后调用（§2.2）；`#newProjectDir` 的失败回滚在 init 之前。
- **Space**：扫描识别「待重建」的视频目录（§5.2）。

### 8.3 git 作为外部工具

- 在受管外部工具的登记表里加 `git`，只检测、不下载，与 ffmpeg 相同（[架构设计 §12.9](../../architecture/architecture-design.md#129-受管外部工具与安装动作)）。查找顺序是环境变量 `BAOCUT_GIT`、用户指定的路径、系统 PATH。版本要求 ≥ 2.30（`--pathspec-from-file`、porcelain v2 已稳定）。
- macOS 上 `/usr/bin/git` 的特殊处理见 §7。
- 用系统的 git 命令行，不内嵌 git 库：用户的忽略规则、属性、LFS、`safe.directory` 与锁的行为都与用户自己的 git 一致，不会因为另一套实现写出 git 认不出的索引。

### 8.4 协议与设置

- **方法**（`projects.history.*`，Runtime 网关）：
  - `status { projectId }`
  - `log { projectId, videoId?, limit, before? }`
  - `save { projectId, name, note? }`
  - `restore { projectId, videoId, commit }`
  - `resolve { projectId, videoId, keep: 'video' | 'snapshot' }`
  - 主题 `projectHistory` 推送状态变化。
  - Web 可用 `status`、`log`、`restore`、`resolve` 与 `save`，它们都只经 Runtime 读写项目。
- **设置**（[架构设计 §5.10](../../architecture/architecture-design.md#510-偏好设置)）：
  - `projects.history.enabled`（默认 `true`）
  - `projects.history.cadence`（`segment` | `turn` | `manual`，默认 `segment`）
  - `projects.history.maxFileMiB`（默认 50）
  - 每个项目的覆盖值记在项目登记里。
- **错误码**：
  - `HISTORY_GIT_MISSING`
  - `HISTORY_PAUSED`（带原因：`locked`、`repo-state`、`local-config`、`disabled`）
  - `HISTORY_CONFLICT`
  - `HISTORY_SNAPSHOT_INVALID`
  - `HISTORY_COMMIT_NOT_FOUND`

### 8.5 体量

按本机现有视频的实测：

- 一部 6 MB 的 `video.db` 里，`document_versions` 占 5.69 MB（9 个版本），其中一份转录有 5 个版本，每个约 950 KB；实体只有约 10 KB。每笔事务另写约 8 KB 的回执、撤销记录与 outbox。
- 这部视频的快照只有各文档的当前版本，约 1–2 MB 文本。
- 一个提交只重写改过的文档。git 用 zlib 存储，JSON 文本通常压到四分之一到六分之一；打包后同一文件的前后版本以差量存储，只改几行的版本只占几 KB。
- 现有视频最多的有 37 笔事务。按工作段合并，这样一次编辑大约是 2–4 个提交；逐笔提交则是 37 个。

## 9. 例子：已有仓库 baoyu-video

`baoyu-video` 是用户自己的仓库：代码合成的源码在 `scenes/` 下，用 `compositions import <videoId> --path scenes/out/<seg>` 导入视频；视频在一块外接盘上；仓库已经忽略了 `.bcut/`、`video.db*`、`video.lock`、`blobs/`、`**/export/**`。

- **情形**：已在仓库里，不 init，归属模式（§2.1）。BaoCut 只往 `.git/info/exclude` 补自己的块，其中的 `**/exports/` 覆盖了用户规则没覆盖的复数形式。
- **提交什么**：各视频的 `.bcut-snapshot/` 进版本。`blobs/` 被用户忽略，BaoCut 不强行提交，收进来的素材在克隆后缺失。用户在 IDE 里改的 `scenes/` 代码不归 BaoCut 提交；智能体在回合里改的，回合前干净的路径随回合提交。
- **链接素材**：在外接盘上，快照里是绝对路径（§3.5）；另一台机器上标为缺失，挂上同名盘或重新链接后恢复。
- **大文件**：这个仓库的 `.git` 有 413 MB、19 个提交，大头是同一套约 12 MB 的字体被反复提交了六次。BaoCut 的门槛（§2.4）不会让自动提交带进这样的文件；它们是用户自己提交的，BaoCut 不碰。

验收要点（实施时写进[验收与测试](../../acceptance/acceptance-spec.md)）：

- 同一状态两次写快照逐字节相同；改一个片段只改一行。
- 删除 `video.db` 后重新打开项目，视频按快照重建，`videoId` 不变，内容与删除前一致（素材缺失的除外）。
- 一段包含 3 个回合、20 笔手工编辑的工作在安静期后只产生 1 个提交，正文列出全部回合与编辑。
- 用户先暂存一个无关文件，自动提交后它仍是已暂存状态，不在提交里。
- `index.lock` 存在时不提交、不删锁，锁释放后的下一个提交点补上。
- 仓库本地配置定义了过滤器时自动提交暂停，而且过滤器命令没有被执行。
- `git pull` 改了一部关着的视频的快照，打开它时导入为一笔「外部变更」，撤销后回到原状态。
- 两边都改时不自动合并，两个选择都按 §5.3 生效。
- 没有 git 时项目照常创建、编辑、导出，快照照写，状态显示原因。
- Windows 上 `core.autocrlf=true` 时检出快照不被误判为外部改动。

## 12. 待评审事项

1. **已有仓库里提交到哪**。本文提交到用户的当前分支。另一种做法是影子分支：用临时索引（`GIT_INDEX_FILE`）、`commit-tree` 与 `update-ref` 把提交写到 `refs/heads/baocut/history`，不碰用户的 HEAD、索引与工作区。代价是快照文件在用户的分支上一直显示为已修改。哪种做默认？
2. **已有仓库默认是否开启自动提交**。本文默认开，以满足「每个项目都有版本记录」。用户自己维护的代码仓库是否应默认关、由用户打开？
3. **合并参数**：安静期 5 分钟、最长 30 分钟、锁重试 5 次 × 2 秒，待实测调整。
4. **大小门槛**：50 MiB。收进来的素材是否默认进版本，还是只让代码包目录进？
5. **Windows 没有 git 时**：是否下载受管的 MinGit。它是多层目录的压缩包，现有解包器只解根目录下的普通文件，需要改。
6. **提交说明**：模板拼接是否够用；是否允许用户选择用模型写摘要（需要模型，有费用）。
7. **本地过滤器暂停**：「暂停 + 在项目设置里显式启用」与产品设计 §3.2.1「不弹信任确认」的口径是否一致。
8. **克隆后的模式**：克隆下来的 BaoCut 新建项目在新机器上按归属模式处理（§2.1）。是否要在仓库里留一个提交进去的标记，让它恢复成全量模式？
