# G0 上游适配报告（2026-10-12）

对应[语义检索规范 v0.1](../../../docs/design/embedding/embedding-retrieval-spec-v0.1.md) §18.3 的 PR 0。脚本、夹具与复现命令见 [README](../README.md)；全部原始指标在 [`g0-2026-10-12-metrics.json`](g0-2026-10-12-metrics.json)，阈值建议在 [`g0-thresholds-proposal.json`](g0-thresholds-proposal.json)。

> 夹具是手写合成集：57 个句群、34 条查询（27 条有答案）、54 个对称对、36 个术语对。**一条查询约等于 3.7 个百分点**，Recall@5/10 在所有配置下都是 1.0（饱和）。本报告能回答“能不能接、前缀用哪套、哪些后端能共用空间”，不能替代 §18.1 的标注集校准；所有阈值都是未校准起点。

## 1. 结论

| 问题 | 结论 | 依据 |
| --- | --- | --- |
| 锁定哪个 `promptPairId` | **`modelcard-v1`**（模型卡 / SentenceTransformers 配置那套）；`litert-docs-v1` 只作实验 profile | 两套在量化后端上检索指标相同，都明显好于不加前缀；`modelcard-v1` 与检查点自带的 `config_sentence_transformers.json` 一致，来源更权威；对称任务同源的 `sym-modelcard` 在数字/否定差异上区分最好（§3、§5） |
| 参考后端与 LiteRT 能否共用 `embeddingSpaceId` | **不能**。参考后端只作为评测基准，产品库只写 LiteRT 向量 | 同一输入余弦中位 0.991、最低 0.963；查询-文档分数平均偏移 0.011，弱命中/重录阈值会整体漂移；混用时 Top-1 一致率只有 0.94–1.0（§4） |
| LiteRT CPU 与 GPU 能否共用 | GPU **显式设 FP32 激活**时可作为同一空间的候选；GPU 默认激活（约等于 FP16）单独记一个 `encoderProfileId`，待标注集确认 | CPU↔GPU-FP32 余弦最低 0.997、分数 Pearson 0.999、Top-1 一致 1.0；CPU↔GPU 默认余弦最低 0.989，`modelcard-v1` 512 维时 R@1 少 1 条（§4） |
| 维度 | 768 为默认，512 为可用的低存储档；引擎 `output_size=512` 与自己截断再归一化逐位一致 | 768 与 512 的检索指标在 litert-cpu、GPU-FP32 与参考 FP32（`modelcard-v1`）上相同；GPU 默认激活 512 维 R@1 少 1 条（§3、§4、§6） |
| Recall@10 下降 ≤ 2pp 门槛 | **本夹具无法判定**：所有混用组合下降都是 0pp，但一条查询就是 3.7pp 且 R@10 饱和 | 需要 §18.1 的标注集 |
| C API 能否作为 Rust FFI 基础 | 能。xcframework dylib 与 Python 轮子逐位一致（最大差 0.0），单个 dylib 只依赖系统框架 | §7 |

## 3. 检索：前缀配对比较

精确前缀字符串（`{q}`/`{t}` 是去掉首尾空白后的原文）：

| `promptPairId` | 查询 | 文档 |
| --- | --- | --- |
| `modelcard-v1` | `task: search result \| query: {q}` | `title: none \| text: {t}` |
| `litert-docs-v1` | `task: search query \| text: {q}` | `task: search result \| text: {t}` |
| `no-prefix`（对照） | `{q}` | `{t}` |

注意两套来源把 `search result` 用在相反的角色上：模型卡用它标查询，LiteRT 文档用它标文档。`modelcard-v1` 与检查点 `config_sentence_transformers.json` 中的 `Retrieval-query` / `query` 与 `document` prompt 完全一致。

量化后端 `litert-cpu`，768 维（27 条有答案查询；R@5、R@10 全部为 1.0，省略）：

| 配对 | R@1 | nDCG@10 | 平均 margin | 无答案最高分 | 有答案最低相关分 | 无答案分离 AUC | exact-word R@1 | paraphrase R@1 | cross-lingual R@1 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `modelcard-v1` | 0.796 | 0.927 | 0.065 | 0.698 | 0.664 | 0.979 | 1.00 | 0.83 | 0.60 |
| `litert-docs-v1` | 0.796 | 0.927 | 0.059 | 0.752 | 0.723 | 0.984 | 1.00 | 0.83 | 0.60 |
| `no-prefix` | 0.759 | 0.908 | 0.044 | 0.758 | 0.680 | 0.947 | 1.00 | 0.83 | 0.50 |

参考后端 `ref-fp32`，768 维：`modelcard-v1` R@1 0.796、nDCG 0.927；`litert-docs-v1` R@1 0.833、nDCG 0.941（多对 1 条跨语言查询）；`no-prefix` R@1 0.759。512 维的数字与 768 维基本相同（见指标 JSON）。

判断：

- 两套前缀都比不加前缀好（R@1 +3.7pp、跨语言 +10pp、margin 与无答案 AUC 都更高）。
- 两套之间的差异在 1 条查询以内，而且方向随后端变化（参考后端偏 `litert-docs-v1`，GPU-FP32 偏 `modelcard-v1`），数据上分不出胜负。因此按来源锁定 `modelcard-v1`：它是检查点自带配置，SentenceTransformers 用户、上游评测和以后的 740m 包都会按这套走。
- `litert-docs-v1` 的分数整体高约 0.05，阈值不能跨配对复用；这也说明 `promptPairId` 必须进入索引身份（规范 §5.3）。
- 失败样本：R@1 未命中的 5 条里，4 条跨语言查询都排到了**同语言的困难负例**之前（q-cl-01→pr-09、q-cl-03→ve-08、q-cl-04→hr-08、q-cl-10→pr-10），1 条 paraphrase（q-pa-06→pr-03）。存在同语言偏置；跨语言检索靠 Top-K 召回能到，靠 Top-1 不够，需要混合召回或重排。

## 4. 跨后端与同一空间判断

同一输入的向量余弦（768 维，845 条输入）与查询-文档分数一致性：

| 对比 | 余弦最低 | p05 | 中位 | 分数 Pearson | 分数平均绝对差 |
| --- | --- | --- | --- | --- | --- |
| ref-fp32 ↔ ref-bf16 | ≥ 0.9999 | — | — | — | — |
| litert-cpu ↔ ref-fp32 | 0.963 | 0.984 | 0.991 | 0.983 | 0.011 |
| litert-cpu ↔ litert-gpu（默认激活） | 0.989 | 0.996 | 0.998 | 0.995 | 0.006 |
| litert-cpu ↔ litert-gpu（FP32 激活） | 0.997 | 0.999 | 1.000 | 0.999 | 0.002 |
| litert-cpu 默认 ↔ litert-cpu FP32 激活 | 1.0 | 1.0 | 1.0 | 1.0 | 0.0 |

混用检索（文档用 A 后端编码、查询用 B 后端，`modelcard-v1`，768 维）：所有组合的 Recall@10 变化都是 0pp（饱和），区别只体现在排序上：

| 文档 ← 查询 | Top-10 重合 | Top-1 一致 |
| --- | --- | --- |
| litert-cpu ← litert-gpu-FP32 | 0.994 | 1.000 |
| litert-cpu ← litert-gpu 默认 | 0.950 | 0.971 |
| litert-cpu ← ref-fp32 | 0.932 | 0.971 |
| ref-fp32 ← litert-cpu | 0.935 | 1.000 |
| litert-gpu 默认 ← ref-fp32 | 0.918 | 0.941 |

结论与理由：

- **参考 ↔ LiteRT 不共用空间。** int4 量化带来的偏移是系统性的：无答案最高分 0.691→0.698、有答案最低相关分 0.647→0.664，对称分数也整体移动。按规范 §5.3，余弦接近 1 不能单独证明可混用；本夹具的 R@10 又无法判定，所以默认分开。产品不会运行参考后端，这不影响上线。
- **CPU ↔ GPU-FP32 是同一空间的候选。** 差异比 CPU 内部的任何可见量化效应都小一个数量级。建议 GPU 后端在设置里显式请求 FP32 激活，并在 §18.1 标注集上复核后再正式合并 `encoderProfileId`。
- **GPU 默认激活单独记 profile。** C API 实测 GPU 默认与 FP32 激活之间余弦最低 0.991；CPU 上默认与 FP32 逐位相同，说明 CPU 默认已是 FP32。

## 7. 延迟、内存与缓存

**测量条件不干净**：同机一直有其他构建任务，两轮测量（2026-10-12 晚与 2026-10-13 00:00–00:10）期间 1 分钟负载均值在 7–44 之间（更早一轮一度到 112）。下表给出两轮的范围；CPU 数字明显受干扰，GPU 数字两轮基本一致。正式性能验收必须在空闲机器上重测。

| 指标 | LiteRT CPU | LiteRT GPU（默认激活） | 参考 FP32（PyTorch CPU） |
| --- | --- | --- | --- |
| 引擎创建 / 模型加载（冷，无缓存） | 0.61–0.75 s | 1.28–1.43 s | 3.3–4.3 s |
| 引擎创建（有缓存） | 0.17–0.65 s | 0.44–0.50 s | — |
| 单条（batch 1，夹具文档句群） | 61–109 ms | 26–29 ms | 63 ms（负载低时）～400 ms |
| batch 16，每条 | 104–118 ms | 26–27 ms | 20–55 ms |
| batch 64，每条 | 102–132 ms | 26–27 ms | 20–42 ms |
| 845 条全部（batch 16） | 84–85 s | 23–24 s | 21–51 s |
| 长输入 6,780 字符（约 2.3k token），`TRUNCATE` | 0.99–1.30 s | 0.18 s | — |
| 同上，`CHUNK_AND_AVERAGE` | 3.4–3.6 s | 0.44 s | — |
| 进程峰值 RSS（创建后 / 结束） | 286 MB / 575–724 MB | 438–447 MB / 590–606 MB | 1.25–1.80 GB |
| 引擎缓存（磁盘） | 70.9 MB（XNNPACK） | 11.2 MB 程序 + 68.4 MB 权重 | — |

C 程序（xcframework dylib，引擎缓存已热）：CPU batch 16 每条 144–149 ms，创建 0.14–0.35 s；GPU 每条 27–32 ms，创建 0.43–0.59 s。BF16 参考在 M2 CPU 上每条 112–158 ms，比 FP32 慢，只作精度对照。

观察：

- GPU 每条约 27 ms，与批量大小无关；本机上 GPU 应是首选后端。
- LiteRT CPU 在负载下批量没有收益，甚至更慢；CPU 线程数可用 `litert_lm_embedding_engine_settings_set_num_threads` 设置，本次没有扫线程数，留给空闲机器重测。
- 模型文件 164.6 MB；加上引擎缓存，CPU 约 236 MB、GPU 约 244 MB 磁盘。RSS 结束值包含 Python 与 numpy，本身不是引擎净占用。
- 规范里的延迟/内存数字是验收设定，本节数字不能直接用于对照验收（负载干扰）。

## 8. C API 调用顺序与 FFI 注意事项

用 xcframework 的 C 头文件写了独立 C 程序（`c-smoke/embedding-smoke.c`），编码同一批 845 条输入后与轮子结果逐向量比较：CPU、GPU 都是**最大绝对差 0.0**，两个不同构建的 dylib 输出一致。

调用顺序（Rust 包装可照此实现）：

```text
litert_lm_set_min_log_level(kLiteRtLmLogSeverityError)
settings = litert_lm_embedding_engine_settings_create(model_path, "cpu" | "gpu", NULL, NULL)
litert_lm_embedding_engine_settings_set_cache_dir(settings, dir)          // 目录必须已存在
litert_lm_embedding_engine_settings_set_activation_data_type(settings,
    kLiteRtLmActivationDataTypeFloat32)                                  // GPU 建议显式设
engine = litert_lm_embedding_engine_create(settings)                      // 失败返回 NULL
litert_lm_embedding_engine_settings_delete(settings)                      // 创建后即可释放
opts = litert_lm_embedding_options_create()          // 实测默认 normalize=1、insert_special_tokens=1、overflow=2（Error）、output_size=-1（全维）
[litert_lm_embedding_options_set_output_size(opts, 512)]
[litert_lm_embedding_options_set_input_overflow_strategy(opts, kLiteRtLmInputOverflowStrategyTruncate)]  // 0=ChunkAndAverage 1=Truncate 2=Error
item = litert_lm_input_data_create(kLiteRtLmInputDataTypeText, utf8, byte_len)   // 复制字节，不需要 NUL
rs = litert_lm_embedding_engine_compute_embedding_batch(engine, requests, counts, n, opts)
     // requests[i] 是 InputData* 数组，counts[i] 是它的长度；一条文字就是长度 1
n  = litert_lm_embedding_responses_get_size(rs)
r  = litert_lm_embedding_responses_get_at(rs, i)
d  = litert_lm_embedding_response_get_size(r); v = litert_lm_embedding_response_get_values(r)  // 指针归 response 所有，先复制再 delete
litert_lm_embedding_responses_delete(rs); litert_lm_input_data_delete(item)
单条：litert_lm_embedding_engine_compute_embedding(engine, items, count, opts) → response，用 response_delete 释放
litert_lm_embedding_options_delete(opts); litert_lm_embedding_engine_delete(engine)
出错：先看返回值（NULL），再在同一线程读 litert_lm_get_last_error_code() / _message()
```

注意事项：

1. **缓存目录必须预先存在且可写**，否则引擎创建失败（“Cache directory does not exist or is not writable”）。CPU 写一个约 71 MB 的 XNNPACK 缓存，GPU 写约 11 MB 程序缓存 + 68 MB 权重缓存；文件名里带模型文件大小和一个数字标识，换模型文件会生成新缓存。产品要把缓存放到模型目录或缓存目录，并计入磁盘占用与清理。
2. **默认最长输入是 1024 token**（签名 128/256/512/1024/2048/8192，默认引擎只加载到 1024），默认溢出策略是**报错**（`kLiteRtLmInputOverflowStrategyError`），调用方只得到泛泛的“Failed to compute embedding.”，具体原因（“Input sequence length exceeds maximum supported signature length (1024)”）只出现在日志里。`max_input_length=2048` 的引擎对约 2342 token 的输入同样失败。BaoCut 自己分块，应保证每块远小于 1024 token，同时把溢出策略设成 `TRUNCATE` 作为兜底，并在 FFI 层把截断记到结果元数据。
3. **GPU 默认激活不是 FP32**：GPU 默认与 FP32 的余弦最低 0.991，CPU 默认等于 FP32。要让 CPU/GPU 落到同一空间，GPU 必须显式设 FP32 激活（§4）。
4. **`output_size` 就是截断再归一化**。FFI 可以始终取 768 维，再在 Rust 侧截断到存储维度，避免同一引擎为不同维度多次计算。
5. **特殊符号由引擎自动加**：传入的字符串只拼任务前缀，不要自己加 `<bos>`/`<eos>`，也不要关 `insert_special_tokens`。
6. **调用方必须先去掉首尾空白**：尾部空白会让向量明显变化（最低余弦 0.947）。
7. **模型元数据里的模态不可信**：`ModelInfo` 对纯文字包也报告 vision=True、audio=True；`.litertlm` 里没有内嵌提示词模板，C API 也没有读取模板的接口。可用模态与前缀只能由 BaoCut 的模型包清单声明（规范 §4.2）。
8. **错误信息是线程局部的“最后错误”**：坏模型路径会让创建返回 NULL，`last_error` 为 `NOT_FOUND … open() failed: … No such file or directory`。头文件规定：成功调用不会清除之前的错误，所以只能凭返回值判断失败，再在同一线程上读取并复制消息（或先调用 `litert_lm_clear_last_error`）。同时引擎会把完整源码位置追踪打到 stderr，需要在 Model Worker 里收集或静音。
9. **后端字符串**是小写 `"cpu"` / `"gpu"`；GPU 在本机走 WebGPU 上的 Metal（适配器“Apple M2, metal-3”）。
10. 单个 dylib 内含 GPU 实现，只依赖系统框架；install name 是 `@rpath/libCLiteRTLM_mac.dylib`，打包时要设置 rpath。通用二进制 137.8 MB，只打 arm64 可约减半（轮子的 arm64 版本 65.7 MB）。

## 9. 失败、缺口与后续

- **未覆盖的 G0 项**：多帧输入与采样顺序、不同模态的归一化（本次只拿到纯文字 270m 包）；740m 包；Windows 与 Intel Mac；规范 §18.3 要求的“实际 SDK 打包大小”只给出 dylib 体积，未做应用级打包。
- **跨后端门槛无法判定**：R@5/R@10 饱和、一条查询 3.7pp。要在 §18.1 标注集上重跑 `score.py` 才能决定 ≤ 2pp 门槛。
- **阈值全部未校准**：只说明分布形状与可分性；翻译记忆阈值在本夹具上几乎没有间隔。
- **延迟受并发负载影响**：测量时同机有其他构建任务（负载均值 6–112 之间波动），CPU 数字偏高且批量结果不稳定；GPU 数字相对稳定。正式性能验收需在空闲机器上重测。
- 长输入：默认引擎对超过 1024 token 的输入直接失败，`max_input_length=2048` 对约 2342 token 的输入也失败（见 §8 第 2 条）。
- 参考后端需要额外安装 pillow 与 torchvision 才能加载（多模态处理器的依赖），已写入 `pyproject.toml`。
