# GPU 编码（文字与画面）：经产品的 Model Worker 复核（2026-10-14）

对应[语义检索规范 v0.1](../../../docs/design/embedding/embedding-retrieval-spec-v0.1.md) §4.4「CPU 与 GPU 路径必须属于已通过一致性门槛的同一空间」。[文字 G0](g0-2026-10-12.md) §4 用 Python 轮子与 C 程序测过 CPU 与 GPU（FP32 激活）的文字向量，结论是“同一空间的候选”；[多模态 G0](g0-multimodal-2026-10-13.md) §5 测过整张图在 GPU 上时帧向量与 CPU 不同空间。本报告用产品自己的路径复核：Runtime 的 `LocalEmbeddingProvider` → Model Worker（`crates/model-runtime` 的 `litert-lm` 后端，C API 经 `dlopen`）→ LiteRT-LM 0.18.0。脚本是 [`device-compare.ts`](../device-compare.ts)；汇总在 [`g0-gpu-2026-10-14-metrics.json`](g0-gpu-2026-10-14-metrics.json)（只有数字，不含文字与向量）。

> **语料小。** `fixtures/` 的 57 个句群（文档）与 34 条查询，共 91 条文字，加一张合成参考帧；§7 另用 60 张真实关键帧与 24 条查询。足以回答“同一份输入在两种设备上出的向量是否可以互相比较”，不能替代 §18.1 的标注集。

## 1. 结论

| 问题 | 结论 | 依据 |
| --- | --- | --- |
| 文字：GPU（FP32 激活）与 CPU 能否共用向量身份 | **能**。91 条逐条余弦最低 0.99857、p10 0.99942、中位 0.99964；34 条查询的第一名全部一致。与 G0 的 0.997 / Top-1 1.0 一致。文字的 `encoderProfileId` 不随设备变，GPU 起不来退回 CPU 也不重算索引 | §2 |
| 画面：主干在 GPU、图像编码器在 CPU 时能否与 CPU 共用帧向量身份 | **能**（同日复测改判）。60 张真实关键帧逐张余弦最低 0.99963、中位 0.99984，比文字的 GPU/CPU 差异还小；查询第一名换位的都是 CPU 上分差 ≤ 0.0015 的近似并列，与已上线的 GPU 查询向量带来的换位同一量级。§3 先按一张合成参考帧对 0.9999 判了“不能”，那是同一设备升级引擎的回归门槛，不是数值类别的门槛。现在带图像编码器加载时主干照样在 GPU，画面的 `encoderProfileId` 不变。整张图在 GPU 上帧向量最低 0.990、前 5 名重合 0.79，不用 | §3、§7 |
| 快多少 | 文字每批 16 条，端到端（含 Worker 往返）中位 CPU 约 1.26–1.28 s、GPU 约 0.51 s，约 2.5 倍；纯引擎（G0 的 C 程序）每条 145 ms 对 27 ms。画面每帧在 Apple M4 上：负载低时 CPU 0.49 s、主干在 GPU 0.47 s（约快 5%，耗时主要在 CPU 上的图像编码器），CPU 被别的进程占满时 0.68 对 0.51 s | §4、§7 |
| 多占多少内存 | 只加载文字编码器时 GPU 多约 80–130 MB 常驻（文字包 375 → 452 MB，多模态包 767 → 894 MB）。带图像编码器时见 §7 | §4、§7 |
| GPU 起不来时 | Worker 在加载里退回 CPU（stderr 说明一次），不报 `MODEL_UNSUPPORTED`，不停用模型包；本机测不出 GPU 失败，由单元测试覆盖 | §5 |

## 2. 文字向量

两次运行只差 `BAOCUT_GPU`：`off` 时 Worker 只报 `cpu`，不设时报 `['metal', 'cpu']`，Runtime 交 `metal` 加载，Worker 用 C API 的 `gpu` 后端并把激活设成 FP32。向量是 Runtime 截到 512 维、重新归一化后的值（与索引里存的一样）。

| 模型包 | 设备 | 条数 | 余弦最低 | p10 | 中位 | 查询第一名一致 | `encoderProfileId` |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `embeddinggemma2-text@litert-lm` | cpu ↔ metal | 91 | 0.99857 | 0.99942 | 0.99964 | 34/34 | 相同 |
| `embeddinggemma2-multimodal@litert-lm` | cpu ↔ metal | 91 | 0.99857 | 0.99942 | 0.99964 | 34/34 | 相同 |

两个包的数字逐位相同，与它们的文字编码器逐位相同一致（`textEncoderSha256`）。差异比 GPU 默认激活（G0：余弦最低 0.989，512 维时 R@1 少 1 条）小一个数量级，所以 GPU 必须设 FP32 激活：C 库没有这个设置时 Worker 不用 GPU。

## 3. 画面向量（首测，已由 §7 改判）

第一次运行时多模态包带图像编码器加载，文字后端设 `gpu`、图像后端设 `cpu`：参考帧余弦 0.999869。图像编码器虽在 CPU，图像 token 仍经主干出向量，主干在 GPU 上。这低于 `reference-vectors.ts` 判定“同一编码实现”的 0.9999，画面的 `encoderProfileId` 写的是 `cpu`，当时改成：`model.load` 带 `vision` 时整个引擎在 CPU，改后第二次运行参考帧余弦 1。代价是画面一路在建或要编码图片时，文字也在 CPU 上算（同一个 Worker），画面建完、Worker 空闲卸下后才回到 GPU。

一张合成图对 0.9999 判不出数值类别：文字共用身份的依据是逐条余弦 ≥ 0.998 且名次一致（§2）。§7 用真实关键帧按同一标准复测，结论改为主干照样在 GPU。

## 4. 速度与内存

| 模型包 | 设备 | 第一批（含加载、预热） | 之后每批 16 条中位 | 常驻峰值 |
| --- | --- | --- | --- | --- |
| 文字包 | cpu | 3.3 s | 1.28 s | 375 MB |
| 文字包 | metal | 2.0 s | 0.51 s | 452 MB |
| 多模态包（只有文字编码器） | cpu | 4.1 s | 1.26 s | 767 MB |
| 多模态包（只有文字编码器） | metal | 3.2 s | 0.51 s | 894 MB |

常驻峰值是每 0.3 秒采样 `ps` 的 RSS；Metal 缓冲区不全算在 RSS 里，GPU 的实际占用可能更高。引擎缓存（`cacheDir`）里 GPU 另写程序与权重缓存（G0：约 11 MB + 68 MB），与 CPU 的 XNNPACK 缓存在同一个目录（`<runtime-home>/cache/litertlm/`）。Worker 是 debug 构建，C 库本身是发布版；机器负载 1.3–4.1。

## 5. 退回 CPU

真实的 GPU 失败在本机复现不了。实现与测试：

- `crates/model-runtime/src/embed/litert.rs` 的 `with_cpu_fallback`：要 GPU 时先在 GPU 上建引擎并预热（GPU 程序在第一次计算时编译），任何一步失败就在 CPU 上再建；CPU 也失败时报 CPU 的错误。测试 `a_failed_gpu_engine_falls_back_to_the_cpu`。
- C 库缺 `litert_lm_embedding_engine_settings_set_activation_data_type` 时不试 GPU。
- `packages/jobs/src/local-embedding.test.ts`「GPU：……」：假 Worker 报 `metal`、模拟 GPU 起不来时，嵌入照常完成、设备报 `cpu`、模型包状态 `ready`。

## 7. 画面：主干在 GPU、图像编码器在 CPU（复测）

§3 只比了一张合成参考帧，门槛借的是 `reference-vectors.ts` 的 0.9999。那是同一设备升级引擎时判“编码实现没变”的回归门槛。文字共用身份的依据是逐条余弦 ≥ 0.998 且名次一致（§2），画面按同一标准复测。路径同上：`LocalEmbeddingProvider.embedImages` → Model Worker（发布构建）。比了三种加载，每种跑两遍：

- **CPU**：`BAOCUT_GPU=off`，主干与图像编码器都在 CPU（§3 改后的做法）。
- **混合**：主干 `gpu`（FP32 激活），图像编码器 `cpu`（现在的做法）。
- **整张图在 GPU**：两个后端都是 `gpu`（FP32 激活）。这是临时构建，没有保留。

素材是本机素材库的 3 部视频（访谈、讲座、演讲），各取 20 张关键帧，与画面一路一样是 512 px JPEG、每批 4 张。查询是 24 条英、中、日文的画面描述（`device-compare.ts` 的 `FRAME_QUERIES`），没有标注，只比两种设备给出的名次。汇总见 [`g0-gpu-2026-10-14-frames-metrics.json`](g0-gpu-2026-10-14-frames-metrics.json)（最终构建的 CPU 对混合，只有数字）。

| 加载 | 帧向量对 CPU 的余弦：最低 / p10 / 中位 | 同一加载重跑 | 查询第一名与 CPU 一致 | 前 5 名重合 |
| --- | --- | --- | --- | --- |
| 混合 | 0.99963 / 0.99973 / 0.99984 | 逐位相同 | 20/24 | 0.95 |
| 整张图在 GPU | 0.99033 / 0.99368 / 0.99716 | 逐位相同 | 20/24 | 0.79 |

两种 GPU 加载的查询向量对 CPU 最低都是 0.99872，与 §2 一致。

**名次差在哪。** 混合下第一名换了 4 条，都是 CPU 上的近似并列，原第一名与新第一名的分差只有 0.0003–0.0015。两帧都出自同一部视频，4 条里 3 条是相邻的两帧。分开看两边：

- 只换帧向量（查询仍用 CPU 的）时换 3 条，分差 0.0003–0.0006。
- 只换查询向量（帧仍用 CPU 的），也就是已上线的“文字在 GPU、画面在 CPU”，同样换 3 条，分差 ≤ 0.0003。

可见混合给帧向量带来的变化，与已经接受的 GPU 查询向量同一量级。整张图在 GPU 时只换帧向量就出现分差 0.0095 的换位，前 5 名重合掉到 0.79。

**速度。** 下表是每帧编码耗时，取每批 4 张的中位，不含取帧。机器是 Apple M4（10 核），§6 记的是 Apple M2。

| 条件 | CPU | 混合 | 整张图在 GPU |
| --- | --- | --- | --- |
| 负载约 23–25（别的会话在编译） | 0.68 s | 0.51 s | 0.42 s |
| 负载约 8–13 | 0.49 s | 0.47 s | 0.40 s |
| 同时一张张取帧（ffmpeg，模拟画面一路的预取），负载 7–22 | 0.67 s | 0.65 s | 0.48 s |
| 最终构建复跑，负载约 9–10 | 0.50 s | 0.48 s | — |

第一批含加载与 GPU 程序编译：CPU 7.1–11.9 s，混合 9.8–17.7 s。

多模态 G0 与协议 §4.5 记的 CPU 每帧约 1.1 秒是在 M2 上测的。估算的参考速度（`DEFAULT_VISUAL_SECONDS_PER_FRAME` = 1.1）没有改：画面一路第一批编完就换成实测速度。

**内存。** 每 0.3 秒采样 Worker 的 RSS，多模态包带图像编码器时的峰值是 CPU 851 MB、混合 1081 MB，多约 230 MB。Metal 缓冲区不全算在 RSS 里。

**结论：**

- 混合与 CPU 属于同一数值类别，差异比文字的 GPU/CPU 还小。所以画面的 `encoderProfileId` 不变，登记的 `cpu` 一段表示 FP32。已建的画面索引不重算，GPU 起不来退回 CPU 时也不重算。参考向量里 `metal` 一项的参考帧更新为混合给出的值（对 CPU 0.999869）。
- 混合在本机只快一点：负载低时约 5%，耗时主要在 CPU 上的图像编码器；CPU 被别的进程占满时约 25%。主要的好处是画面一路在建时，文字（讲话索引、搜索查询）不再被挤回 CPU。
- 整张图在 GPU 还能再快 15–30%，但帧向量最低只有 0.990、前 5 名重合 0.79。用它要单独的 `encoderProfileId`（全部画面索引重建），还要标注集复核检索质量，所以暂不采用。
- 没做：带标注的画面 R@k（`frames-eval` 标注集不在本机）。

复现：

```bash
BAOCUT_GPU=off node --experimental-strip-types tools/embedding-eval/device-compare.ts --models <models> --tools <runtime-home>/tools --frames <frames-dir> --out cpu.json
node --experimental-strip-types tools/embedding-eval/device-compare.ts --models <models> --tools <runtime-home>/tools --frames <frames-dir> --out gpu.json
node --experimental-strip-types tools/embedding-eval/device-compare.ts --compare cpu.json gpu.json
```
