# GPU 文字编码：经产品的 Model Worker 复核（2026-10-14）

对应[语义检索规范 v0.1](../../../docs/design/embedding/embedding-retrieval-spec-v0.1.md) §4.4「CPU 与 GPU 路径必须属于已通过一致性门槛的同一空间」。[文字 G0](g0-2026-10-12.md) §4 用 Python 轮子与 C 程序测过 CPU 与 GPU（FP32 激活）的文字向量，结论是“同一空间的候选”；[多模态 G0](g0-multimodal-2026-10-13.md) §5 测过 GPU 的帧向量与 CPU 不同空间。本报告用产品自己的路径复核：Runtime 的 `LocalEmbeddingProvider` → Model Worker（`crates/model-runtime` 的 `litert-lm` 后端，C API 经 `dlopen`）→ LiteRT-LM 0.18.0。脚本是 [`device-compare.ts`](../device-compare.ts)；汇总在 [`g0-gpu-2026-10-14-metrics.json`](g0-gpu-2026-10-14-metrics.json)（只有数字，不含文字与向量）。

> **语料小。** `fixtures/` 的 57 个句群（文档）与 34 条查询，共 91 条文字，加一张合成参考帧。足以回答“同一份输入在两种设备上出的向量是否可以互相比较”，不能替代 §18.1 的标注集。

## 1. 结论

| 问题 | 结论 | 依据 |
| --- | --- | --- |
| 文字：GPU（FP32 激活）与 CPU 能否共用向量身份 | **能**。91 条逐条余弦最低 0.99857、p10 0.99942、中位 0.99964；34 条查询的第一名全部一致。与 G0 的 0.997 / Top-1 1.0 一致。文字的 `encoderProfileId` 不随设备变，GPU 起不来退回 CPU 也不重算索引 | §2 |
| 画面：文字在 GPU 时能否同一个引擎里在 CPU 上编码帧 | **不能**。图像编码器设成 CPU，参考帧向量与纯 CPU 引擎的余弦是 0.999869，低于参考向量回归的 0.9999（图像向量还要经过主干，主干在 GPU 上）。所以带图像编码器加载时整个引擎在 CPU，画面索引只用 CPU 建；改后参考帧余弦 1 | §3 |
| 快多少 | 每批 16 条，端到端（含 Worker 往返）中位 CPU 约 1.26–1.28 s、GPU 约 0.51 s，约 2.5 倍；纯引擎（G0 的 C 程序）每条 145 ms 对 27 ms | §4 |
| 多占多少内存 | 只加载文字编码器时 GPU 多约 80–130 MB 常驻（文字包 375 → 452 MB，多模态包 767 → 894 MB）。带图像编码器时都在 CPU，不变 | §4 |
| GPU 起不来时 | Worker 在加载里退回 CPU（stderr 说明一次），不报 `MODEL_UNSUPPORTED`，不停用模型包；本机测不出 GPU 失败，由单元测试覆盖 | §5 |

## 2. 文字向量

两次运行只差 `BAOCUT_GPU`：`off` 时 Worker 只报 `cpu`，不设时报 `['metal', 'cpu']`，Runtime 交 `metal` 加载，Worker 用 C API 的 `gpu` 后端并把激活设成 FP32。向量是 Runtime 截到 512 维、重新归一化后的值（与索引里存的一样）。

| 模型包 | 设备 | 条数 | 余弦最低 | p10 | 中位 | 查询第一名一致 | `encoderProfileId` |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `embeddinggemma2-text@litert-lm` | cpu ↔ metal | 91 | 0.99857 | 0.99942 | 0.99964 | 34/34 | 相同 |
| `embeddinggemma2-multimodal@litert-lm` | cpu ↔ metal | 91 | 0.99857 | 0.99942 | 0.99964 | 34/34 | 相同 |

两个包的数字逐位相同，与它们的文字编码器逐位相同一致（`textEncoderSha256`）。差异比 GPU 默认激活（G0：余弦最低 0.989，512 维时 R@1 少 1 条）小一个数量级，所以 GPU 必须设 FP32 激活：C 库没有这个设置时 Worker 不用 GPU。

## 3. 画面向量

第一次运行时多模态包带图像编码器加载，文字后端设 `gpu`、图像后端设 `cpu`：参考帧余弦 0.999869。图像编码器虽在 CPU，图像 token 仍经主干出向量，主干在 GPU 上。这低于 `reference-vectors.ts` 判定“同一编码实现”的 0.9999，画面的 `encoderProfileId` 写的是 `cpu`，所以改成：`model.load` 带 `vision` 时整个引擎在 CPU。改后第二次运行参考帧余弦 1。

代价：画面一路在建或要编码图片时，文字也在 CPU 上算（同一个 Worker）。画面建完、Worker 空闲卸下后，再加载只带文字编码器，又回到 GPU。

## 4. 速度与内存

| 模型包 | 设备 | 第一批（含加载、预热） | 之后每批 16 条中位 | 常驻峰值 |
| --- | --- | --- | --- | --- |
| 文字包 | cpu | 3.3 s | 1.28 s | 375 MB |
| 文字包 | metal | 2.0 s | 0.51 s | 452 MB |
| 多模态包（只有文字编码器） | cpu | 4.1 s | 1.26 s | 767 MB |
| 多模态包（只有文字编码器） | metal | 3.2 s | 0.51 s | 894 MB |

常驻峰值是每 0.3 秒采样 `ps` 的 RSS；Metal 缓冲区不全算在 RSS 里，GPU 的实际占用可能更高。引擎缓存（`cacheDir`）里 GPU 另写程序与权重缓存（G0：约 11 MB + 68 MB），与 CPU 的 XNNPACK 缓存在同一个目录（`<runtime-home>/cache/litertlm/`）。Worker 是 debug 构建，C 库本身是发布版；机器负载 1.3–4.1。

## 5. 退回 CPU

真实的 GPU 失败在本机复现不了。实现与测试：

- `crates/model-runtime/src/embed/litert.rs` 的 `with_cpu_fallback`：要 GPU 时先在 GPU 上建引擎并预热（GPU 程序在第一次计算时编译），任何一步失败就在 CPU 上再建；CPU 也失败时报 CPU 的错误。测试 `a_failed_gpu_engine_falls_back_to_the_cpu`。
- C 库缺 `litert_lm_embedding_engine_settings_set_activation_data_type` 时不试 GPU。
- `packages/jobs/src/local-embedding.test.ts`「GPU：……」：假 Worker 报 `metal`、模拟 GPU 起不来时，嵌入照常完成、设备报 `cpu`、模型包状态 `ready`。
